Run these in your game's folder. Builds go to `dist/<target>/` there, and `--out DIR` puts them
elsewhere.

| Target | Command | You get |
|---|---|---|
| Windows | `kulisa build windows` | `<Title>.exe` with your icon, and `game.kpak` next to it |
| Linux | `kulisa build linux` | the program and `game.kpak` |
| macOS | `kulisa build macos` | `<Title>.app` with your icon, for Apple silicon and Intel |
| Web | `kulisa build web` | a folder to put on any static web host |
| Android | `kulisa build android` | an APK (`--abi arm64-v8a,x86_64` to add the emulator), or with `--aab` an App Bundle for Google Play |
| iOS | `kulisa build ios` | an `.app` (`--sim` for the simulator), and an `.ipa` when it has App Store signing |

Any computer can build for Windows, Linux, macOS and the web. See
[Installation](../install/#other-platforms) for what Android and iOS need.

<Aside type="caution" title="Building on Windows for Linux or macOS">
Programs on those systems need an "executable" mark, which a folder on Windows cannot hold. The
build also writes `dist/<Title>-linux.tar.gz` or `dist/<Title>-macos.tar.gz`, which keeps the mark.
Ship that, not the folder. Signing a Mac app takes a Mac, so without one Macs warn about the app
and ask players to allow it.
</Aside>

Linux players need what desktop systems normally have: ALSA, udev, a Vulkan or OpenGL driver, and
`libxkbcommon-x11` on X11. A very minimal system may need them installed.

With a tool [built from source](../install/#from-source), players are compiled for each build:
add `--release` to anything you share, and `--universal` for a Mac app that also runs on Intel.

## Try it on a device

```sh
kulisa run --web            # build for the web and serve it with live reload
kulisa run --android        # build, install and start on a phone or emulator (adb)
```

`kulisa run --web` prints a local address; open it in a browser. Saving a file reloads the
game there too.

## What goes into a build

`kulisa pack` (and every build) packs the game folder into one `game.kpak`: your scripts,
stories, images, sounds, fonts and shaders. `dist/`, dot-files and [videos](#videos) stay out. The settings in
`kulisa.toml` become the app's name, version, ids and orientation:

```toml
[game]
id = "cat_tales"          # save folder and app ids
title = "Cat Tales"       # window title and app name
version = "1.0.0"         # shown to players
build = 1                 # raise it for every store upload
icon = "icon.png"         # a square PNG, 1024x1024 ideally

[android]
package = "com.example.cattales"

[ios]
bundle_id = "com.example.cattales"
```

## Videos

Videos (`.mp4`, `.m4v`, `.mov`, `.webm`) stay out of `game.kpak`, which is read into memory whole.
Builds put them beside it, and they are read as they play. If you only run `kulisa pack`, keep them
next to the `.kpak` yourself, at the same paths as in the game.

Use MP4 with H.264 video and AAC sound, which every system plays. Each platform decodes it with its
own decoder, so the engine stays small and phones use their hardware.

Linux has no decoder every system is sure to have, so `kulisa build linux` and `kulisa run` convert
your videos to AV1 and Ogg Vorbis with [FFmpeg](https://ffmpeg.org/download.html), on your computer.
They keep the results in `.video-cache` in your game's folder and convert again only when a video
changes. Players need nothing installed.

## Publishing on the web

The web build is plain files: `index.html`, the player (`kulisa.js` and `kulisa_bg.wasm`) and
`game.kpak`. Any static host works: GitHub Pages, itch.io (zip the folder as an HTML game),
Netlify, Cloudflare Pages or your own server. The player needs no special server headers.
Audio starts with the player's first click or key, as browsers require.

On phones and tablets the game fills the visible screen, and the first tap makes it
fullscreen, without the browser's bars, where the browser allows it. In fullscreen the screen
also locks to the game's orientation, so a landscape game turns sideways by itself. iPhone
Safari allows neither; there the game fits around the address bar (classic-vn asks the
player to turn the phone, using `kulisa.screen.mismatch`), or players can add it to the home
screen to play without the bar.

## Signing for stores

Without these settings builds still run on your own devices, but stores refuse them and other
people's computers warn about them.

<Aside type="caution" title="Keep your keys out of your game's repository">
`kulisa pack` never puts `.jks`, `.keystore`, `.p12`, `.pfx`, `.p8`, `.pem`, `.key` or
`.mobileprovision` files in a game, but a public repository would still expose them. Paths in
`kulisa.toml` are relative to the game, so keep keys in a folder outside it. `kulisa.toml`
itself ships in the game, so never put a password there.
</Aside>

### Google Play

Make an upload key once, and keep it safe:

```sh
keytool -genkeypair -keystore ../keys/upload.jks -alias upload -keyalg RSA -keysize 2048 -validity 10000
```

Name it in `kulisa.toml`:

```toml
[android]
package = "com.example.cattales"
keystore = "../keys/upload.jks"
key_alias = "upload"
```

Then set `KULISA_KEYSTORE_PASSWORD` in your environment (and `KULISA_KEY_PASSWORD` if the key has
its own password), and build:

```sh
kulisa build android --release --aab
```

Upload `dist/android/<id>.aab`, and raise `build` for every upload. Your whole game goes in the
bundle's base module, which Google Play limits to 500 MB compressed. Above 200 MB, players on
mobile data see a warning before installing.

### macOS, outside the Mac App Store

You need an Apple Developer account and a **Developer ID Application** certificate. Save your
notary credentials once:

```sh
xcrun notarytool store-credentials cat-tales
```

Then name both in `kulisa.toml` and build:

```toml
[macos]
bundle_id = "com.example.cattales"
identity = "Developer ID Application: Your Name (TEAMID)"
notary_profile = "cat-tales"
```

```sh
kulisa build macos --release --universal --notarize
```

Share `dist/macos/<Title>.zip`, which holds the notarized app. This is for distributing outside
the Mac App Store, which needs sandboxing that Kulisa does not set up yet.

### App Store

You need an Apple Developer account, an **Apple Distribution** certificate, an App Store
provisioning profile for your bundle id, and Xcode 26 or newer. Your game also needs an icon.

```toml
[ios]
bundle_id = "com.example.cattales"
identity = "Apple Distribution: Your Name (TEAMID)"
provisioning_profile = "../keys/cat-tales.mobileprovision"
```

```sh
kulisa build ios --release
```

Upload `dist/ios/<Title>.ipa` with Apple's Transporter app.

### Steam

You need a Steamworks account and its SDK (Kulisa ships none of Valve's files). Name them in
`kulisa.toml`, and `kulisa build` and `kulisa run` find the Steam library in the SDK folder:

```toml
[steam]
app_id = 480            # your app id; 480 is Valve's test app
sdk = "../steamworks"   # the folder with public/ and redistributable_bin/
```

Achievements and stats go through [`kulisa.steam`](https://github.com/nikolchaa/Kulisa/blob/main/docs/API.md#steam):

```luau
kulisa.steam.unlock("FINISHED_CHAPTER_1")
```

The same script runs everywhere: without Steam those calls do nothing.

**Cloud saves** need no code. In Steamworks, under *Steam Cloud*, turn on Auto-Cloud and add one
root, then an override for each other system so saves follow players between them:

| System | Root | Subdirectory |
|---|---|---|
| Windows | `WinAppDataRoaming` | `<id>` |
| macOS (override) | `MacAppSupport` | `<id>` |
| Linux (override) | `LinuxXdgDataHome` | `<id>` |

`<id>` is your game's `[game] id`, and the pattern `*` with *Recursive* on covers saves and
settings alike.
